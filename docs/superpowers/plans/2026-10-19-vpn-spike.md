# VPN MikroTik — Spike Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Membuktikan dengan perangkat nyata (radpro, dua VPS hub, satu MikroTik v7)
bahwa jalur API dan RADIUS lewat hub bekerja tanpa NAT, bahwa auto switch di router
berjalan, dan mengunci teks script RouterOS yang akan dirender service.

**Architecture:** Semua dikonfigurasi dengan tangan. Tidak ada kode produk. Core
berupa interface `wg-core` di host radpro, yang dibuat dari container sementara
`--network host`. Host radpro tidak punya `wg`, dan paket host sengaja tidak
dipasang. Hub berupa `wg-nm` + `wg-up` di masing-masing VPS. Di router, script
ditulis tangan.

**Tech Stack:** WireGuard (kernel), `wireguard-tools` + `nftables` di container
alpine, RouterOS v7, k3s NodePort, FreeRADIUS netmanager.

**Spec:** `docs/superpowers/specs/2026-10-19-vpn-mikrotik-design.md`

## Global Constraints

- Backhaul `10.99.0.0/24`: core `10.99.0.1`, hub A `10.99.0.2`, hub B `10.99.0.3`.
- Router uji `/32`: `10.100.0.10`. Admin `10.99.128.0/24` (tidak dipakai di spike).
- Port: core UDP `51822`, hub UDP `51821`. **Jangan pakai 51820**, karena itu milik tikman.
- MTU: `wg-nm` 1420, `wg-up` 1380.
- RADIUS: `10.99.0.1`, auth `30812`, acct `30813`, timeout 3000 ms.
- Hub me-route, **tidak me-NAT**, dan aturan forward-nya stateless.
- Script router: tidak ada `/tool fetch` atau `/import`. Routing table khusus
  `netmanager-vpn` dengan rule `lookup-only-in-table`.
- radpro adalah host produksi bersama (k3s netmanager, tikman, Jenkins). Setiap
  perintah di radpro harus disetujui pemilik saat dijalankan. Semua yang dibuat di
  sana dibongkar di Task 9.
- Nilai rahasia (private key, secret RADIUS, password) tidak ditulis ke repo
  (netmanager repo publik di GitHub). Catatan hasil di Task 9 hanya memuat nama dan
  angka.

## Review Focus

- Router uji ternyata memakai policy route atau mangle sendiri, sehingga trafik ke
  `10.99.0.1` ikut table lain. Rule `lookup-only-in-table` harus tetap menang.
  Task 4 memeriksanya dengan `/ip route check`.
- Paket RADIUS sampai di pod dengan source IP node, bukan `10.100.0.10`, karena
  ada SNAT di jalur. Ini dicek di log FreeRADIUS (Task 5), bukan hanya dari login
  yang berhasil, karena catch-all `clients.conf` bisa menutupi masalahnya.
- Accounting terikat ke router lain milik tenant lewat fallback `findRouterByNasIp`
  ("router mana saja milik tenant"). Task 5 mengecek `nasipaddress` di `radacct`.
- Fragmentasi lewat dua tunnel: paket API besar (daftar PPP secret) macet
  sementara ping kecil lancar. Task 6 menguji dengan ping DF berukuran besar dan
  `/ppp/secret/print` lewat API.
- Hub hidup lagi saat router sudah pindah: core sempat melihat dua handshake segar
  dan memilih hub lama. Task 7 menyalakan hub A kembali dan memeriksa bahwa `/32`
  tetap di hub B.

### Task 3: nftables stateless di hub

**Files:**
- Create: `docs/superpowers/specs/2026-10-19-vpn-hub.nft` (ruleset yang terbukti, dipakai sebagai golden di rencana service)

- [ ] **Step 1: Tulis ruleset** `table inet netmanager_vpn` berisi:
  - chain `forward` (hook forward, policy accept), dengan rule berurutan:
    - `iifname "wg-nm" oifname "wg-up" ip daddr 10.99.0.1 udp dport { 30812, 30813 } accept`
    - `iifname "wg-nm" oifname "wg-up" ip daddr 10.99.0.1 icmp type { echo-request, echo-reply } accept`
    - `iifname "wg-nm" oifname "wg-up" ip daddr 10.99.128.0/24 icmp type echo-reply accept` (admin bisa ping router)
    - `iifname "wg-nm" tcp flags & (syn | ack) == syn drop`
    - `iifname "wg-nm" oifname "wg-up" ip daddr { 10.99.0.1, 10.99.128.0/24 } tcp sport { 8728, 8291, 22 } accept`
    - `iifname "wg-nm" drop`
    - `iifname "wg-up" oifname "wg-nm" ip saddr { 10.99.0.1, 10.99.128.0/24 } accept`
    - `iifname "wg-up" oifname "wg-nm" drop`
  - chain `input` (hook input), dengan rule:
    - `iifname "wg-nm" icmp type echo-request accept`
    - `iifname "wg-nm" drop`

  Tidak ada `ct state` di hub.
- [ ] **Step 2: Pasang di kedua hub** dengan `nft -f docs/.../vpn-hub.nft`, lalu cek dengan `nft list table inet netmanager_vpn`.
- [ ] **Step 2b: Chain `wgcore_in` di core (radpro).** Pasang ruleset `RenderCore()` (golden `internal/firewall/testdata/core.nft` di repo service): chain `wgcore_in` (`type filter hook prerouting priority -150`, sebelum DNAT NodePort kube-proxy di -100) dengan rule berurutan:
    - `iifname "wg-core" ct state established,related accept`
    - `iifname "wg-core" ip saddr 10.100.0.0/14 ip daddr 10.99.0.1 udp dport { 30812, 30813 } accept`
    - `iifname "wg-core" ip saddr 10.100.0.0/14 ip daddr 10.99.0.1 icmp type { echo-request, echo-reply } accept`
    - `iifname "wg-core" ip saddr 10.99.128.0/24 ip daddr 10.100.0.0/14 accept`
    - `iifname "wg-core" drop`

  Cek dari hub A (alamat backhaul-nya): `nc -zv -w2 10.99.0.1 6443`, `nc -zv -w2 10.99.0.1 10250` dan satu NodePort harus timeout; `curl http://10.99.0.1:7480/healthz` dari pod core tetap jalan, dan RADIUS dari router (Task 5) tetap lewat. Konfirmasi `ct state` bekerja di prerouting -150 dengan `nft monitor trace` bila ragu.
- [ ] **Step 2c: Cek sintaks dengan nft sungguhan.** Di hub dan di radpro: `nft -c -f hub.nft` dan `nft -c -f core.nft` (keduanya keluaran `RenderHub()`/`RenderCore()`, sama dengan golden `internal/firewall/testdata/`).
Expected: keduanya keluar 0 tanpa pesan. Ruleset belum pernah diperiksa nft sungguhan.
- [ ] **Step 2d: Policy FORWARD Docker di hub.** Di hub yang menjalankan Docker: `iptables -S FORWARD | head -1` menunjukkan `-P FORWARD DROP`. Tanpa accept, ping admin → router lewat hub harus gagal; setelah `iptables -I DOCKER-USER -i wg-nm -o wg-up -j ACCEPT` dan `iptables -I DOCKER-USER -i wg-up -o wg-nm -j ACCEPT` harus berhasil, sementara drop di tabel nft (misalnya SYN dari router ke `10.99.0.1:22`) tetap berlaku. Periksa juga backend: `iptables -V` di container service (alpine) dan di host harus sama-sama `(nf_tables)` atau sama-sama `(legacy)`; bila beda, container tidak melihat chain `DOCKER-USER` milik Docker dan langkah accept dilewati diam-diam. Lakukan hal yang sama di radpro untuk `-i wg-core -o wg-core` bila ada Docker di sana.

### Task 7: Auto switch hub A → hub B

**Files:**
- Create: `docs/superpowers/specs/2026-10-19-vpn-router-switch.rsc` (scheduler yang terbukti, dengan placeholder untuk kunci)

- [ ] **Step 1: Daftarkan router di hub B** dengan kunci yang sama (`wg set wg-nm peer <routerPub> allowed-ips 10.100.0.10/32`).
- [ ] **Step 2: Tulis scheduler `netmanager-vpn-switch`** (interval 20s) dengan perilaku:
  1. Ping `10.99.0.1` dengan `src-address=10.100.0.10`, `count=5`, `interval=1`. Kalau ≥ 4 balasan, berhenti.
  2. Tandai server aktif gagal dengan `[/system resource get uptime]`. Hasilnya disimpan di global `nmVpnFail` sebagai array `host → uptime`.
  3. Pilih entri **berikutnya** (berurutan, melingkar) dari daftar `{ "host|port|pubkey"; ... }` yang tidak gagal dalam 5 menit.
  4. Kalau semua gagal, pilih entri pertama.
  5. `/interface wireguard peers set [find comment=netmanager-vpn] endpoint-address=... endpoint-port=... public-key=...`.
  6. `:log warning "netmanager-vpn: pindah ke <host>"`.
- [ ] **Step 3: Simulasikan pengendali core dengan tangan.** Jalankan loop shell di container core: setiap 10 s, baca `latest-handshake` router dari kedua hub (`ssh hub wg show wg-nm latest-handshakes`), lalu pindahkan `10.100.0.10/32` ke peer hub dengan handshake terbaru (< 180 s) memakai `wg set wg-core peer ... allowed-ips ...`. Tujuannya membuktikan aturan "handshake terbaru" sebelum dijadikan kode.
- [ ] **Step 4: Matikan hub A** dengan `ip link set wg-nm down` di hub A, sementara sesi PPPoE uji sedang aktif.
Expected:
- dalam ≤ 60 s, log router menunjukkan "pindah ke hub B";
- loop core memindahkan `/32` dalam ≤ 20 s setelah itu;
- sesi PPPoE yang aktif tidak putus;
- login PPPoE baru berhasil;
- test koneksi API dari netmanager sukses.

Catat setiap waktunya.
- [ ] **Step 5: Hidupkan lagi hub A**, tunggu 3 menit.
Expected: router tetap di hub B, `/32` tetap di hub B, dan tidak ada log pindah baru.
- [ ] **Step 6: Ulangi Step 4 dengan mematikan VPS hub B seluruhnya** (shutdown dari panel provider).
